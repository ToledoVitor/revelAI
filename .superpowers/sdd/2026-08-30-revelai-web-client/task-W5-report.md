## Delivered behavior

- `/free-training` remains an isolated, canonical owner route. Home creates one exact Free payload, `{ "mode": "free" }`; trailing/redundant slashes canonicalize before mount, and the Free screen has neither competitive control nor competitive vocabulary.
- Free creation is causal rather than time/list based. Before its first request the browser proves session storage through a separate probe key, then stores only a UUID `Idempotency-Key` in `sessionStorage`; it stores neither athlete identity, media, nor secrets. The health check never reads, replaces, or clears the owner/intent facts. A get throw or silent null/no-op fails closed without mutating a response-lost key or issuing POST; after recovery the exact persisted key is reused. No timestamp marker, clock comparison, or `listAttempts` adoption remains.
- The API accepts the optional public `Idempotency-Key` header, documents it in OpenAPI, and persists a key/fingerprint scoped by athlete. SQLite's unique partial index plus transaction boundary returns the same Attempt for replay/concurrency, remains valid after reopen, and maps a conflicting key/payload safely to `invalid_request`. Callers with no key and existing verified behavior remain compatible.
- A persisted known owner resumes with authoritative `getAttempt`: awaiting-upload returns to capture (media must be reselected), uploaded/processing returns to pending polling, and valid/failed returns to terminal. A matching owner `attempt_not_found` clears the matching Free ownership pair and creates a fresh causal Free Attempt; other safe errors remain retryable. Unrelated attempts, wrong modes, stale records, and malformed stored data are never adopted.
- A tombstoned replay retains its server-side causal mapping but returns parsed `attempt_not_found`; it never resurrects the Attempt. The Free client clears that stale intent and stops. A user-selected retry durably persists a distinct UUID before making the new POST. An intent without an owner follows the same path.
- If storage get/set/remove throws or silently does nothing, Free creation fails closed with an accessible message and no POST. The ownership cleanup operation records probe health but still attempts and independently verifies both owner and intent removal; only healthy, fully verified cleanup is `cleared`. Start-another, tombstone, stale-owner, and delete paths block on cleanup failure; an explicit retry repeats the complete cleanup. When storage later becomes available, the explicit retry either reuses the preserved causal key or, after confirmed pair cleanup, creates one fresh durable key and one request.
- Exact-id deletion ownership probes storage before reading or matching owner state. Consequently a global get throw or silent null yields `unavailable`, never a misleading `not-owned`, and leaves both raw ownership facts intact. A direct Free 204 remains on Free with an accessible retry rather than navigating; recovery clears both and only then creates fresh.
- History deletion synchronously serializes same-tick activation. A successful delete clears Free owner/key only when its id matches the persisted owner. If that cleanup is unavailable, History retains a visible accessible cleanup action and blocks further destructive actions; its retry uses that exact deleted id, restores completion status and heading focus, then permits a fresh Free Attempt. Deleting a different history entry cannot destroy the current Free owner.
- The complete upload lifecycle is neutral at `lib/attempt-flow/upload-lifecycle`: its controller, XHR/fetch progress, cancel, duplicate/lost-response classification, authoritative GET reconciliation, and generation invalidation are shared by W4 verified and W5 Free. Mode-specific calibration/capture/result renderers remain at their edges. The existing neutral MIME/media module remains outside verified-owned code.
- Shared pending polling clears `refreshing` when a request is stopped, disabled, or superseded by another generation, so a new Free or W4 pending Attempt keeps `Atualizar agora` enabled and does not inherit stale `Atualizando` state.
- Existing W5 behavior remains: narrow local media validation, source-to-wire metadata, preview URL cleanup, one multipart part, actual owner progress, retry/cancel/reconciliation, 1/2/4/5 polling with focus/visibility/manual coalescing, safe approximate Free result/provenance/tips, all cross-mode arms fail-closed, failure retryability, fresh begin, deletion error/retry/stale safety, and accessible headings/status/focus.
